# Smol Machines Sandbox Tools

Give an agent an isolated computer with `SmolExecTool`, `SmolPythonTool`, and `SmolFileTool`. The tools run in local microVMs by default; set `target="cloud"` to use Smol Machines Cloud. All three use the same VM API, so an agent can move between local development and hosted execution.

## Installation

```shell
uv add "crewai-tools[smol]"
```

Local execution needs Linux with `/dev/kvm` or an Apple Silicon Mac. Cloud execution needs `SMOL_CLOUD_TOKEN` on the worker.

## Basic use

```python
from crewai import Agent
from crewai_tools import SmolExecTool

agent = Agent(
    role="Developer",
    goal="Implement and test a feature",
    backstory="Build and verify changes in an isolated computer.",
    tools=[SmolExecTool()],
)
```

Each tool call creates and deletes a VM by default. Set `persistent=True` to retain state between calls, and close the VM when finished:

```python
from crewai_tools import SmolExecTool, SmolFileTool

shell = SmolExecTool(target="cloud", persistent=True)
try:
    shell.run(command="echo hello > /workspace/message.txt")
    files = SmolFileTool(target="cloud", machine_id=shell.active_machine_id)
    print(files.run(action="read", path="/workspace/message.txt"))
finally:
    shell.close()
```

The attached file tool never deletes the VM owned by `shell`. `SmolPythonTool` accepts `code` and optional `argv`, `env`, and `timeout`. The file tool accepts `read` and `write`; use `binary=True` for base64 data.

Guest networking is enabled by default for workloads that need network access, including package installs. Set `network=False` to block guest egress. Local and Cloud VMs can still start from registry images because the image is retrieved outside the guest. The local target remains local even when Cloud credentials are present. See the tool package README for additional lifecycle examples.

To avoid pulling a registry image on a local VM, supply a local rootfs directory or a `docker save` archive through `image`.
